## 1. 事実の更新（4章「現状ステータス」への追記候補）

### 1-1. 公式ファームウェアのバージョンが2.24.0まで進行（既存記載の2.23.4から更新）

現ARCHITECTURE.mdは「2.21.0、2.23.4等」と記載。その後継として**2.24.0**が確認できた。主な追加内容：

- **予測タイマー・ラップ統計のSD/フラッシュへの永続化**：トラックごとに保存され、電源再投入直後から予測タイマーが機能する（従来はウォームアップ待ちが必要だった）
- GPSサンプル品質の改善（重複サンプルの削減、解像度向上）
- WiFi/BLE安定性の改善、Lua用メモリの追加確保

**Phase 5への示唆**：現在のPhase 5タスク（5-1〜5-6）には「ラップ統計の永続化」に relevantなタスクが明示されていない。5-2「トラック情報の保存先を決める」の中に、**ベストラップ・予測タイマー状態もSD/不揮発領域に保存する設計を含めるべきか**、検討の余地あり（公式実装がここに専用の改善を割いていることから、実用上重要な機能と推測される）。

### 1-2. MK2/MK3のハードウェア設計データ（回路図・PCB）は非公開と確認

`RaceCapture-Pro_firmware`はソースコードのみ公開で、対応する基板の回路図・PCBデータは見当たらなかった。オープンなハードウェア設計データが存在するのは**MK1のみ**（`RaceCapturePro_MK1`リポジトリ、CC BY-SA）。MK1は当時のGPSサンプリングが10Hz（MK2以降は50Hz）と、性能面でも見劣りする世代。

**含意**：これは**現行プロジェクトの「ハードウェアはESP32でフルスクラッチ設計、MK2/MK3を物理的に模倣しない」という方針を裏付ける根拠**になる。新規タスクは不要だが、7章「未解決事項」に判断根拠として1行残す価値はある。

## 2. 既存方針を裏付ける追加根拠（変更不要、参考情報）

### 2-1. RaceCapture AppのRaspberry Pi実行は公式サポート範囲内

Autosport Labs公式Wikiに`RaceCapture on Raspberry Pi`という専用ページがあり、以下が確認できた：

- Raspberry Pi 3/4/5に対応、専用インストーラあり（現状「実験的（experimental）」「エキスパートモード」と明記されているが、機能自体は公式にメンテナンスされている）
- **「本体ハードウェアのどの世代（MK2〜MK4、PodiumConnect含む）とも互換」**と明記
- **ネットワーク経由でのPodiumへのライブテレメトリーも、Android/iOS版と同様に動作**（フォーラムでの開発者(Brent Picasso氏)の回答で確認）
- 実際に複数ユーザーが「常設ダッシュボード化（$100程度）」の事例を報告

**含意**：`ARCHITECTURE.md`の「表示ユニット：Raspberry Pi + タッチパネル」という選定は、公式に前例のある構成であり、実現可能性リスクは低いと判断してよい。新規タスクは不要。

### 2-2. ESP32-S3への全面移行は、実質「ハードウェアクローン」と同じ作業量になる

STM32（元のRCPが使用）とESP32-S3はアーキテクチャが根本的に異なる（Cortex-M系 vs Xtensa/RISC-V系）ため、「基板だけ似せて頭脳だけESP32にする」場合でも、結局はHAL層の全面書き直しとロジック層の移植が必要になる。つまり「ハードウェアをRCPに似せる」ことに追加のメリットはほぼない。

一方、ESP32-S3は以下の点でむしろ有利：
- FreeRTOSベースである点はRCPファームウェアと共通（ロジック層の移植親和性が高い）
- USB OTGネイティブ内蔵（`ARCHITECTURE.md`側でも必須要件として既出）
- TWAI(CAN)コントローラをネイティブ内蔵（外付けはトランシーバICのみで済む）

**含意**：現行の「ESP32-S3を本番採用し、ロジックを移植する」という方針は妥当。追加タスクは不要だが、**移植時は`platform/mk2`等のHAL依存コードと、MCU非依存のロジックコード（lapStats等）の分離状況を確認し、ロジック側を優先的に参照・移植する**という進め方を明記しておくとよい（4章末尾の「ラップタイム計算の実装主体」の項目に1行追記候補）。

## 3. 現状ロードマップに含まれていない新規論点（要ユーザー判断）

### 3-1. 予測タイム計算アルゴリズムの実装方針（Phase 5関連、実装ヒント）

Phase 5（5-3, 5-4）は「実装する」ことは明記されているが、**どう実装するか**の設計メモがない。壁打ちで整理した構造は以下の3ブロック：

1. **スタート/フィニッシュ・セクター判定**：ジオフェンス（緯度経度+半径）通過を検出。ただしGPSサンプル間隔そのままだと精度が粗いため、**通過前後2点のGPS座標を距離で線形補間し、サブサンプル精度で通過時刻を算出**する。公式ファームウェアが「GPSが10Hz未満の場合にアップサンプリングする」という改善を入れているのも同じ精度問題への対処と推測される。
2. **トラックDB**：公式は数十件のトラックDBを持つが、個人利用ならスタート/フィニッシュ座標の手動設定のみで十分。ARCHITECTURE.md 7章の「トラック情報の保存先」検討時に、DB化は不要という判断の参考に。
3. **予測タイム**：ベストラップを「累積走行距離→経過時間」の対応表として保持し、現在位置の走行距離に対応する時間を補間して現在の経過時間との差分（デルタ）を出す。ここが実装上最も作り込みが必要な部分。

**推奨タスク追加**：`task_phase5_breakdown.md`に、上記3ブロックの分解と「①のみ先行実装→アプリでの表示確認→③を追加」という段階的な進め方を明記することを推奨。

### 3-2. セルラー経由の「遠隔からのライブテレメトリー監視」は現状スコープ外

`ARCHITECTURE.md`には**遠隔監視（セルラー経由でピット等から車両状態を見る）の記載が一切ない**。現状の設計は「車載ダッシュボード（RPi表示）」止まりであり、これは公式RaceCapture/Podiumが持つ「セルラー経由の遠隔監視」機能とは異なるスコープ。

壁打ちの中で、これは実装するなら以下の設計が妥当という結論に至った：

- **信頼性の分離**：ローカルSD記録＝絶対に止めない主系統、セルラー経由のライブ配信＝ベストエフォートの副系統、という現行方針（「画面が落ちてもログは止めない」）をそのまま延長し、**ライブ配信が落ちても実害はローカル記録に及ばない**設計にする
- モデム接続は自前でATコマンド制御を書くより、**Linux（Raspberry Pi）+ ModemManagerのような枯れた接続管理スタックに乗る**方が信頼性で有利（公式ファームウェア自身も何年もかけてセルラー再接続ロジックを作り込んでいる経緯があり、自前実装は苦労が大きい）
- 参考になるオープンソース先行事例：**Open Vehicle Monitoring System (OVMS)**（車載機がセルラー+GPSを内蔵し、SDとサーバーの両方に記録、専用アプリで遠隔監視、MQTT対応）

**要ユーザー判断**：この機能をスコープに含めるかどうか自体が未決定。含める場合は新規Phase（例：Phase 6）としてタスク分解が必要。

### 3-3. GPLライセンスに関する留意事項（低優先度）

`RaceCapture-Pro_firmware`はGPLライセンス。ロジック層（lapStats等）を**実装の参考に読む**だけであれば問題ないが、**コードを直接移植・流用する場合、将来リポジトリを公開したり配布したりする際にはGPLの copyleft義務（ソース開示義務等）が生じる可能性がある**。現状は個人利用・プライベートリポジトリなので実害はないが、7章の未解決事項リストに低優先度で1行残しておくと将来の判断に役立つ。

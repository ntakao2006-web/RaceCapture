# Lintarohさんへの共有メモ：車載CAN（CAN1）の取りこぼし（2026-11-04、未送）

Ver.2（UNO Q）で、車載CAN（CAN1）のフレームがずっと約0.8%取りこぼされています。
**本体の設定・ファームは何も変えずに**、ログと設定を読むだけで調べました。
どこで落ちているか・10/19や10/24と何が違うか・直し方の案（RAMへの影響つき）をまとめます。**相談したいことは7章**です。
SUGO（11/8）まではファームを変えない前提です（6章）。

---

## 1. 結論

- 落ちているのは**FDCAN1のRX FIFO0（3件）があふれるところ**です。ソフトの待ち行列（`can1Queue`、128件）でも、Linuxへ渡す文字列の枠（12,000文字）でもありません。**SDにもeMMCにも残っていません。**
- 取り込みスレッド（`can1Capture`、優先度2）が**ときどき約0.7〜1msのあいだ回ってこない**ため、100msごとの長い連続送信（10〜14件が続けて流れる）の途中でFIFOが満杯になり、次の1件が落ちています。ほとんどが1件ずつの欠けです。
- 「`k_usleep(100)`がtickの細かさで実際は長い」という見立ては外れでした。ローダーのtickは**10,000Hz**で、`k_usleep(100)`は100〜200µsです（5章）。
- **同じファーム・同じ新しい基板・同じ車・同じバスの混み方で、10/24は欠け0件**でした。欠けが出ているのは**11/3以降**です。何がスレッドを止めているかは、読むだけでは特定できませんでした（4章）。
- 直し方の第一候補は、**RX FIFO1も使ってFIFOを3件→6件にする**ことです。STM32のRAM（データ）は増えず、増えるのはコード数十〜百バイト程度です（6章 案1）。

## 2. 何が起きているか（数字）

2026-11-04 06:00〜07:00ごろ、NCECに本体をつないだ状態（CAN1は毎秒約690件）で測りました。

| 測ったもの | 結果 |
|---|---|
| STM32が起動してから約11.5時間の合計 | `can_counts[0]` 16,076,418件、`can_overflow[0]` 114,409件（0.71%） |
| 60秒の測定（3回） | `can_overflow[0]`が+230・+246・+108（30秒）。CAN2は+0 |
| 同じ60秒の`can_counts[0]`の増え方とeMMCのCAN生ログの行数 | **一致**（例：41,309件と41,309行）。Linuxへ渡す枠では落ちていない |
| NCECの`0x211`のbyte7（1フレームごとに+1するカウンタ）の飛び | **0.77〜0.86%欠け**（+2の飛びがほとんど、+3がまれ）。`can_overflow`の割合より少し多い（6章の注） |

欠けはIDによって偏っていて、**100ms周期のIDほど多く落ちます**（長い連続送信の後ろの方にいるため）。

| ID | 中身（`docs/design/ncec_can_spec.md`） | 周期 | 欠け |
|---|---|---|---|
| `0x200` `0x201` `0x215` `0x4B0` | アクセル・回転数・車速・4輪速 | 10ms | 0.0〜0.2% |
| `0x211` | ローリングカウンタ | 10ms | 約0.8% |
| `0x231` `0x4EC` | クラッチ・未解明 | 25ms | 1.3〜2.2% |
| `0x240` `0x420` | 水温・スロットル・吸気温 | 100ms | 2〜4% |
| `0x4FF` | ASCII文字列 | 100ms | 6〜8% |

## 3. どこで落ちているか（切り分け）

| 確かめたこと | 結果 | 分かること |
|---|---|---|
| `can_counts[0]`の増え方とeMMCの行数 | 一致 | `frame()`の中の文字列の枠（12,000文字）では落ちていない |
| 欠けたフレームの前後±3msに、ほかのIDのフレームが記録されているか | **毎回3件以上ある**（中央値7件）。全IDが同時に消える区間は最大10ms（バスの自然なすき間）だけ | 待ち行列（128件）があふれるには、メインループが約185ms止まる必要があり、そのときは全IDがまとめて消えるはず。**それは起きていない** |
| 待ち行列にたまっているか（eMMCのCAN生ログで、CAN2の行の直前にあるCAN1の行との時刻の差。CAN1は待ち行列を通り、CAN2は通らない） | 約4分半のCAN2の2,642行すべてで0〜9ms（満杯なら約185ms遅れるはず） | 待ち行列はほぼ空のまま流れている |
| 欠けの直前の様子 | 欠けの直前に、3〜4件を同じ1msでまとめて読んでいる。欠けの直前4msのフレーム数は平均5.2件（ふだんは3.5件） | FIFOに3件たまってから読んでいる＝スレッドが約0.7ms以上遅れた。混んでいるときに落ちる |
| `can_overflow`の増え方と、IDごとの抜けの見積もり | 60秒で+230と約265件、+246と約278件 | ほぼ同じ。RF0L側の数え方（下の注）を考えると、落ちているのはRF0Lの方 |

注：`canOverflow[0]`は、RF0Lが立っていたら1回の見回りで1つ数えます。見回りの間に2件以上落ちると少なく数えるので、`can_overflow`は欠けの**下限**です（0x211のカウンタの方が少し多いのはこのため）。

## 5. 今のファームの作りから分かること

本体のArduinoコア0.52.0のローダーの設定（`zephyr-arduino_uno_q_stm32u585xx.config`）を読みました。

- `CONFIG_SYS_CLOCK_TICKS_PER_SEC=10000`（tickless、SysTick）。`k_usleep(100)`は100〜200µs
- スレッドの優先度：取り込み2、LTE 4、メインループ（main）5、Bridgeの更新5、SD保存6。**取り込みスレッドより上にあるアプリのスレッドは無い**。上にいるのは割り込みと、協調スレッドのシステムワークキュー（-1）だけ
- CAN1のフレームは最短でも約0.23ms間隔（8バイト・500kbps）。FIFOが3件なので、**約0.7ms以上回ってこないと落ちる**
- したがって、約0.7〜1msのあいだ、割り込み・割り込み禁止の区間・協調スレッドのどれかがCPUを取っていることになる。スケッチとRouterBridge・RPCliteのライブラリには、そうなる箇所（`irq_lock`・`k_sched_lock`・割り込みの中のログ出力など）は見つかりませんでした
- ログは`CONFIG_LOG_MODE_IMMEDIATE=y`で、コンソール・シェルはUSART1です。割り込みの中でログが出るとその場で文字を送り切るので疑ったが、出ているかは確かめていません
- **割り込みでの取り込みは今のローダーではできません**：`CONFIG_DYNAMIC_INTERRUPTS`が無く、CANのドライバも入っていないので、スケッチ（LLEXT）からFDCAN1の割り込みを登録する手段がありません

## 6. 直し方の案

RAMの余裕について：10/9の本番イメージの静的領域は**130,105B**です。`README.md`の記録では、130,365Bまでは起動し、130,601Bはエラーを出さずに起動しませんでした。**確かめてある余裕は約260B**です（128KiBまでの約1KBは使えません）。コードもこの領域に入ります。

| 案 | すること | RAMへの影響 | 見込み |
|---|---|---|---|
| **1. RX FIFO1も使う（第一候補）** | 標準IDのフィルター1個（クラシック、ID=0x001・マスク=0x001で奇数IDをFIFO1へ）と拡張IDのフィルター1個を置き、`RXGFC`の`LSS=1`・`LSE=1`、合わないIDは今まで通りFIFO0へ。取り込みスレッドで両方のFIFOを読み、`RF1L`も数える | データは0B（メッセージRAMは別）。コード数十〜百バイト | FIFOが3件→6件、許せる遅れが約0.7ms→約1.4msに。今の欠けはほとんど「1件だけ足りない」なので、大半は消える見込み。NCECの奇数・偶数IDの量は毎秒約350件ずつで釣り合っている |
| 2. 欠けを2種類に分けて数える（案1と一緒に） | RF0L/RF1Lと待ち行列あふれを別の数にし、`/api/status`に出す | 数バイト＋コード | 直したあとに、どちらで落ちているかがすぐ分かる |
| 3. 止めている犯人を探す診断版（試験用） | 取り込みスレッドの見回りの間隔の最大値（`k_cycle_get_32()`）と、500µsを超えた回数を数える。超えたときに、メインループ・Bridge・SD保存のどれが何をしていたかの印も数える | 数十バイト＋コード。試験のあいだだけ | 犯人が分かれば、元を直せる。自宅で車のイグニッションをONにすれば測れる |
| 4. 割り込みで取り込む（長期） | ローダーを`CONFIG_DYNAMIC_INTERRUPTS`かCANドライバ入りで作り直して書き込み、RF0N割り込みで待ち行列へ入れる | 取り込みスレッドのスタック1,536Bが要らなくなり、**RAMは増える方** | 根本的。ただしローダーごと変わるので、基板全体の確かめ直しが要る。SUGOのあと |
| 5. 記録の止め・開始のあいだもCAN1を流す | `execute()`の`LOG0`の待ち（最大20秒の`delay(1)`）の中で`can1Poll()`を呼ぶ | コード十数バイト | 11/3 20:33Zに、記録の止め・開始の前後で全IDがまとめて抜けた区間が1回あった（約50秒の区間で8%）。これが待ち行列のあふれかは未確認 |

やらない方がよいこと：
- `k_usleep(100)`を短くする・休まずに回す：今の欠けは待ちの長さではなく、ときどき回ってこないことが原因なので効きません。優先度2で休まずに回すと、メインループ・Bridge・SD保存が止まります
- 待ち行列（128件）を大きくする：今の欠けはFIFO側なので効かず、RAMを使います

案1の形の例（参考。フィールドの位置はRM0456で確かめてください）：

```c
// can1Init() の CCE を立てたあと（メッセージRAM: 標準フィルター0x000、拡張フィルター0x070、FIFO0 0x0B0、FIFO1 0x188）
volatile uint32_t *sf=(volatile uint32_t *)SRAMCAN_BASE, *ef=(volatile uint32_t *)(SRAMCAN_BASE+0x70);
sf[0]=(2UL<<30)|(2UL<<27)|(1UL<<16)|1UL;   // SFT=クラシック, SFEC=FIFO1, SFID1=0x001, SFID2(マスク)=0x001
ef[0]=(2UL<<29)|1UL; ef[1]=(2UL<<30)|1UL;  // EFEC=FIFO1, EFID1=1 / EFT=クラシック, EFID2(マスク)=1
FDCAN1->RXGFC=(1UL<<16)|(1UL<<24);         // LSS=1, LSE=1, 合わないIDはFIFO0（ANFS=ANFE=0）
// can1Capture(): RXF0S/RXF0A/0x0B0 と RXF1S/RXF1A/0x188 を同じ処理で読み、RF0L・RF1Lを数える
```

2つのFIFOを交互に読むので、同じ1msの中ではIDの並びが前後することがあります（同じIDは必ず同じFIFOなので、IDごとの順番は崩れません）。

## 7. SUGO（11/8）までの扱いと、相談したいこと

SUGOまでは**ファームを変えません**。影響は、回転数・車速・4輪速が0.1〜0.2%程度、水温が2〜4%（10Hzのうち時々1つ抜ける）、クラッチが1〜2%で、画面の表示・Podiumへの送信（10Hz）・あとからの解析には目立たない大きさです。

相談したいこと：
1. **案1（FIFO1も使う）を、SUGOのあとに入れてよいか**。入れるなら案2（欠けを2種類に数える）も一緒に入れたいです。RAMの余裕（約260B）に収まるかは、ビルドの`image-audit.json`で見てください
2. **約0.7〜1ms止める犯人に心当たりがあるか**。新しい基板の工場出荷のローダーが、本体のコアの`firmwares/`の版と同じかも気になっています（読み出すには`flash-mcu.sh`と同じくルーターを止める必要があるので、まだしていません）
3. ファームを変えずにできる切り分けとして、CAN1が流れている状態で次を2分ずつ試し、欠けが消えるか見たいです（どれも本体の状態を一時的に変えるので、ユーザーの了承を取ってから）
   - センサーハブ（CAN2）を外す
   - HDMI表示・RaceCaptureアプリ（`racecapture-*`）と焼き込み録画（`ecologger-video`）を止める
   - カメラをつないで実際に録画している状態でも測る（11/4時点、カメラをつないでCAN1が流れている状態ではまだ一度も測っていない。録画中はLinuxの負荷がずっと高い）

## 8. 確かめ方

`tools/dev/can1_loss/can1_loss.py`（読むだけ。本体の設定・ファームは変えない）：

```
python tools/dev/can1_loss/can1_loss.py                    # 本体（ssh unoq）で60秒はかる
python tools/dev/can1_loss/can1_loss.py --seconds 180
python tools/dev/can1_loss/can1_loss.py --dir drive_logs/20261024   # PCに回収したCAN生ログを数える
```

`/api/status`の`can_counts`・`can_overflow`の増え方、eMMCのCAN生ログの行数、0x211のカウンタでの欠け、IDごとの欠けを出します。直したあとに同じ車で測り、0x211の欠けが0になれば直っています。

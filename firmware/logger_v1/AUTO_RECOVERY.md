# RaceCapture 自動復帰ツールの動作

更新日：2026年8月31日

## 何をするものか

USB接続が一時的に切れた後、RaceCaptureが開いたままデータ取得を再開しなくなる症状に対して、
取得停止を検出してRaceCaptureを正常終了・再起動する補助ツールです。
RaceCapture本体の実行ファイルは改造していません。

正式な走行記録はロガーのSDカードに保存します。自動復帰はPC側の表示・取得を戻すためのもので、
停止中のRaceCaptureの記録をSDから補完する機能はありません。

## 使い方

デスクトップの **「RaceCapture（自動復帰）」** をダブルクリックします。

- RaceCaptureが起動していなければ、起動して監視します。
- 既に1個起動していれば、そのアプリを監視します。
- 2個以上起動している場合は、対象が曖昧になるため開始しません。余分なアプリを閉じてください。
- 監視ツールは裏で動きます。同じWindowsセッションでの監視ツールの重複起動を防ぎます。
- RaceCaptureを自分で閉じると、監視も終了します。勝手に起動し直すことはありません。

普通のRaceCaptureのショートカットから起動しても使用できます。ただし、それだけでは監視は始まりません。
後から「RaceCapture（自動復帰）」を実行すれば、既に開いているアプリに監視を付けられます。
Windows起動時に自動常駐する設定は追加していません。

## 何を見て「止まった」と判断するか

約2秒ごとに、次の情報を確認します。

| 確認するもの | 確認方法・目的 |
| --- | --- |
| RaceCaptureが動いているか | 起動・監視対象のプロセスを確認します。 |
| アプリに新しいデータが保存されたか | `%APPDATA%\racecapture\datastore.sq3` を読み取り専用で開き、`datapoint` の最新IDが変わるかを見ます。 |
| アプリのセッション記録が有効か | `%APPDATA%\racecapture\prefs.json` の `record_session` が文字列の `"1"` かを確認します。 |
| USBのCOMポートが存在するか | Windowsのデバイス名を照会します。現在の監視対象は **COM10固定** です。 |

画面のGPS位置が動いたかどうかでは判断しません。静止中でも、アプリ内のデータ追加が続いていれば正常扱いです。
COMポートは開かないので、監視ツールがRaceCaptureとシリアル通信を取り合うことはありません。

## 自動復帰する条件と手順

次の条件がすべてそろった場合に、再起動を試みます。

1. 監視開始後、アプリ内の最新データIDが変わった実績がある。
2. アプリのセッション記録設定が有効になっている。
3. 最新データIDの更新が **25秒以上** 止まっている。
4. 監視対象のCOMポートが **5秒以上連続して存在** している。
5. 直近10分間の自動再起動が3回未満である。

25秒と5秒の待ち時間は並行して数えます。毎回「切断から30秒後」に復帰するという意味ではありません。
確認周期やアプリの起動時間も加わります。また、USB切断そのものを観測していなくても、
これらの条件を満たす取得停止は復帰対象になります。

復帰するときは、対象のRaceCaptureのウィンドウへ通常の終了要求（Windowsの `WM_CLOSE`）を送ります。
最大15秒待ち、終了を確認できた場合だけ同じ実行ファイルを起動し直します。
未保存内容や確認画面がある場合、自動保存や確認ボタンの操作はしません。

15秒以内に終了しない場合は、強制終了せず監視を終了します。
再起動後は、再びデータIDが変わることを確認してから、次の停止に対する監視を有効にします。
これにより、起動直後から受信できないアプリを際限なく再起動することを避けます。

## できないこと・注意点

- **USBケーブルや電源の瞬断自体は直しません。** ロガーの電源が落ちれば、SD記録も止まります。
- SDの停止・取り出し準備・削除・フォーマット、本体リセット、ファームウェア書込みは行いません。
- RaceCaptureの取得が止まっていた期間は、PC側の記録に空白が生じます。必要なデータはSD側で確認します。
- アプリが最初からデータを保存できない場合、または再起動後もデータ保存が始まらない場合は自動復帰しません。
- アプリのセッション記録設定がOFFの場合、表示だけを監視して復帰させることはできません。
- データベースを読めない回は判定を見送ります。設定ファイルを読めない場合は記録OFFとして扱います。
- RaceCapture自体がクラッシュして終了した場合も、監視は終了します。プロセス終了からの自動復旧は対象外です。
- COM10の存在確認は、USB機器の識別や通信成立の確認ではありません。ポート番号が変わった場合は設定変更が必要です。
- 自動復帰はアプリを閉じるため、編集中の未保存設定があるときは注意してください。
- 補助ツール自身はデータを外部送信しません。RaceCapture本体の通信機能・設定とは別です。

GPS/IMUダッシュボードの追加は別の設定作業です。このショートカットを起動するたびに、
ダッシュボードやアプリ設定を作り直す処理はありません。

## ファイル構成と動作記録

起動の順番は、デスクトップのショートカット → CMD → PowerShell → Pythonの監視ツールです。

| ファイル | 役割 |
| --- | --- |
| [tools/RaceCapture_AutoRecovery.cmd](tools/RaceCapture_AutoRecovery.cmd) | ショートカットから呼ばれる入口です。 |
| [tools/start_racecapture_guard.ps1](tools/start_racecapture_guard.ps1) | 既存アプリの有無を確認し、監視ツールを裏で起動します。 |
| [tools/racecapture_guard.py](tools/racecapture_guard.py) | 取得停止の判定・正常終了要求・アプリ再起動を行います。 |
| [artifacts/racecapture_guard.jsonl](artifacts/racecapture_guard.jsonl) | 日時付きの動作記録です。1行が1件のJSONになっています。 |

主な動作記録は次のとおりです。

| `event` | 意味 |
| --- | --- |
| `started` | 監視開始。対象のプロセスIDとCOMポートも記録します。 |
| `acquisition_stalled` | 復帰条件を満たす取得停止を検出しました。 |
| `restarted` | アプリを再起動しました。新しいプロセスIDも記録します。取得再開の確認とは別です。 |
| `normal_close_failed_no_force_kill` | 通常の終了ができなかったため、強制終了せず断念しました。 |
| `stopped` | 監視を終了しました。 |

起動時の例外など、すべての失敗がこの記録に残るわけではありません。
画面が起動しないときは、まず実行ファイルとPythonの場所、アプリの重複起動を確認します。

現在の既定値は次のとおりです。

- RaceCapture：`C:\Program Files (x86)\RaceCapture\racecapture.exe`
- Python：`%USERPROFILE%\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe`
- 監視ポート：`COM10`
- 更新停止の判定：25秒。Python側には `--port`、`--timeout`、`--exe` の変更用引数があります。
  現在のPowerShellランチャーはこれらを渡さず、既定値で起動します。

この構成は現在のPCの配置に依存します。RaceCaptureやプロジェクト、Pythonを移動した場合は、
ランチャーやショートカットの参照先を更新する必要があります。

## 実機で確認した範囲

2026年8月31日、b版ファームウェアでUSBだけを1秒切断する診断を行い、取得停止を再現しました。
監視ツールが20:54:59に停止を検出し、20:55:02にアプリを再起動しました。
その後、アプリ内へのデータ追加と有効なGPS位置の取得再開を確認しました。

この試験の前後87秒間で、ロガーは再起動せず、同じSDファイルへ8,637行を追加しました。
SDの欠落・エラーの増加はありませんでした。実際のケーブル接触不良や電源断を網羅した試験ではありません。

判定ロジックの試験は [tests/test_pc_tools.py](tests/test_pc_tools.py) にあります。

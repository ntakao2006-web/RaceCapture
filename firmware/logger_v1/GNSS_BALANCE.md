比較処理は最初の条件で中断しました。約15 Hzとの比較・最適設定の決定は未完了です。

2026-09-01。ユーザーの希望は「10 Hz固定」ではなく、軌跡を途切れず記録できる範囲で更新も細かくすることです。
最適な設定は未確定です。以前の散歩ログはGPS中心の25 Hzだけで、別設定との比較データにはなりません。

過去のe版の良好な91.2秒区間を今回の評価処理でも読み直すと、2,281測位すべて40 ms間隔、
新鮮な位置100%、使用衛星中央値9でした。25 Hzが常に処理落ちしているわけではありません。
一方、この良好区間だけでは歩行中の途切れや他設定に対する優劣は評価できません。

## 現在の結論

最初の比較候補は **GPS＋Galileo＋BeiDou B1C・約15 Hz** と **4系統・10 Hz** です。
GLONASSがよく受かる場合に備え、GPS＋Galileo＋GLONASS・約15 Hzも同じ条件で比較します。
これは仕様から選んだ候補で、実測で優劣が付いたという意味ではありません。

衛星システムの数は、実際に測位に使える衛星数とは異なります。弱い信号や反射波が増えても
位置が改善するとは限りません。使用衛星数だけを最大化せず、測位の継続性を優先して選びます。

現在はi版 `logger-v1-gnss-stream-20260901i`、起動設定は暫定の `four_10` です。
4系統10 Hzでの記録継続を実測しましたが、最適値としての採用決定ではありません。
今回の受信途中ではGLONASSを使用でき、BeiDouは使用0機だったため、次の比較候補は `glo_15` です。

## 比較候補

すべて高性能クロック設定済みのこの個体向けです。GPSに加えてQZSS/SBASも有効にします。
設定の「系統数」はGPS・Galileo・BeiDou・GLONASSの数を指し、QZSS/SBASは別に扱います。

| 設定ID | 衛星システム | 試す更新頻度 | メーカー上限 | 比較の目的 |
|---|---|---:|---:|---|
| `b1c_15` | GPS＋Galileo＋BeiDou B1C | 67 ms＝14.925 Hz | 16 Hz | 3系統と細かい更新の両立。上限に少し余裕を持たせる |
| `glo_15` | GPS＋Galileo＋GLONASS | 67 ms＝14.925 Hz | 16 Hz | 同じ更新周期でB1CとGLONASSの受信実績を比較 |
| `four_10` | GPS＋Galileo＋BeiDou B1C＋GLONASS | 100 ms＝10 Hz | 10 Hz | 4系統を利用する基準候補 |
| `four_8` | 上と同じ4系統 | 125 ms＝8 Hz | 10 Hz | 4系統のまま処理に余裕を持たせた効果を見る |
| `dual_20` | GPS＋Galileo | 50 ms＝20 Hz | 20 Hz | 更新を細かくした場合の測位維持率との比較 |
| `gps_25` | GPS | 40 ms＝25 Hz | 25 Hz | これまでの衛星構成・周期を同じg版で再測定する対照 |
| `b1i_10` | GPS＋Galileo＋BeiDou B1I | 100 ms＝10 Hz | 12 Hz | B1Cとは異なる信号・衛星集合の比較。必要な場合に追加 |

`dual_10`（GPS＋Galileo・10 Hz）も用意しています。高性能クロックを読取り確認できない場合の
安全な起動用です。標準クロック個体で上表の高速設定を選ぶ操作は拒否します。

上限16 Hzは整数msでは62.5 msになるため、今回は上限を狙わず67 msとします。
「約15 Hz」と表示しても厳密な15.000 Hzではありません。評価は読戻した67 msを基準にします。
4系統で10 Hzから8 Hzへ下げても受信対象そのものは増えません。処理余裕や欠落率が変わるかを調べる比較です。
メーカーの上限値は通常条件で最低98%の測位更新を前提としており、欠落ゼロの保証ではありません。

## 測定方法

1. アンテナを屋外の同じ位置・向きに固定し、同じ電源・ケーブルで測ります。
   RaceCaptureと自動復帰補助は閉じ、アプリ再起動による影響を避けます。
2. まず `four_10 → b1c_15 → glo_15`、次に順番を逆にして各設定を少なくとも2回測ります。
   全候補について同じ待機時間120秒、その後180秒の記録を使います。
   未測位の設定だけ都合よく長く待たないでください。これは暖機後の比較で、コールドスタート時間の試験ではありません。
3. `four_10` と `four_8` を比べ、10 Hzで更新欠落があるなら余裕を増やす効果を確認します。
   必要なら `dual_20` と `gps_25` も追加します。
4. JCA002のGLONASS帯域の実効受信は型番だけから断定しません。衛星システム別の使用数と
   受信強度を見て判断します。B1Iの比較ではB1C/GLONASSを同時に有効にしません。
5. 静止試験で残った上位2候補を、同じ散歩ルートで順序を替えて再比較します。
   条件が変わるため別時刻の1回だけで決めず、見通しの良い場所と建物付近を含めます。
6. 採用設定で再起動・長時間SD記録・RaceCapture表示を確認し、その設定を起動時の既定値へ反映します。
   この最終採用と既定値変更は、まだ行っていません。

評価の優先順位は次の通りです。

- 新しい有効な位置が得られていた時間割合、最長の途切れ、異常な位置飛び。
- `GPSTow` の更新から算出した実測更新頻度・欠落率。SD100 Hzの重複行を測位回数に数えません。
- 静止時の位置の広がり（95%半径）と `GPSHAcc` の95パーセンタイル。
  前者は再現性、後者は受信機自身の誤差推定です。どちらも真の絶対位置精度の実測ではありません。
- 実際の使用衛星数の中央値・下位10%、システム別使用数。
- IMU100 Hz・SD100 Hzが維持され、SD欠落やGNSS再設定が増えていないこと。

比較ツールの暫定通過条件は、新鮮な位置99%以上・測位更新98%以上・最長途切れ1秒以内、
記録系の検証合格です。これはメーカーの性能保証値ではなく、今回の比較用の選別基準です。
1回だけの結果では採用せず、2回以上通過した設定の位置の広がり・移動時の軌跡を確認し、
同程度なら更新頻度の高い方を選びます。閾値未達を他の良い値で帳消しにする総合点は使いません。

## g版の設定切替と安全範囲

- `getGnssProfiles` は候補と対応可否、`getGnssDiagnostics.configuration` は実設定の
  `profileId`、`periodMs`、`navigationHz`、`verified` を返します。
- `setGnssProfile` はA105のUARTだけで受け付けます。SD記録を止めて正常終了を確認し、
  `confirm: GNSS_PROFILE_TEST` と対応する `id` を指定する必要があります。
- 切替中は古い位置を無効化し、GNSSを安全な1 Hzへ下げてから衛星構成を変え、600 ms待って
  目標周期を設定します。受信機RAMの読戻し一致まで成功とは扱いません。
- 設定変更による一時的な再捕捉は比較区間から分けます。IMU処理は継続します。
  SDの変更前後は別ファイルで、`.meta.json` の `gnss_at_file_open` に設定を記録します。
- 設定選択は電源断で消えます。今回、走行中の自動切替や最適設定の自動保存は実装していません。
- OTP再書込み、NVS消去、SD削除、回路変更、CAN送信は行いません。
  旧e版へ戻すときに、新しい周期を保存したNVSとの互換性には注意してください。

## 操作と結果ファイル

Windowsの既存Python/pyserial環境から実行します。書込みは凍結したg版アプリの0x10000だけです。
以下は接続後の手順で、この文書作成時点では実行していません。

```text
python firmware/logger_v1/tools/gnss_profile.py list --port COM8
python firmware/logger_v1/tools/gnss_profile.py select --port COM8 --profile b1c_15 --settle-seconds 120
python firmware/logger_v1/tools/verify_gnss_health.py --port COM8 --download-port COM10 --seconds 180 --comparison-report --output <新規の試験結果フォルダー>
```

選択ツールはSDを正常終了して設定を変え、変更前に記録中であればSDを再開します。
比較記録の `--comparison-report` は、未測位や更新欠落があっても結果を保存する指定です。
`acceptance_passed: false` を合格として扱いません。通信・ファイル取得の失敗は引き続きエラーになります。
UTC確定でログが途中分割され、取得区間が予定時間の90%未満になった結果は比較対象から外して再測定します。

```text
python firmware/logger_v1/tools/compare_gnss_profiles.py <試験1/verification.json> <試験2/verification.json> ... --stationary --output <新規の比較結果フォルダー>
```

`comparison.csv` と `comparison.json` に各条件の指標と繰返し試験の通過状況を保存します。
歩行ログでは `--stationary` を付けません。自動で最適値を断定したり、書き込んだりはしません。
入力ログや既存結果を上書きしません。

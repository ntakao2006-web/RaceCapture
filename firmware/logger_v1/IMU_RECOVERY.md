# IMU取得停止の調査と自動復旧

更新日：2026年8月31日

追記：21:47の[屋外GNSS再確認](GNSS_OUTDOOR_CHECK.md)で、診断未実施の実運用中に内部エラー5を
1回自動復旧し、その後100Hzで動作している状態も確認しました。以下の意図的な停止試験とは別の証拠です。

## 確認した問題

SDの `LDFC3BA92_0001.csv` を全行読み戻したところ、63,941行のうち63,855行が
`IMULink=0`、`IMUErr=5` で、加速度・角速度・姿勢などの値が欠測になっていました。
有効なIMU値は起動後約1.388～1.488秒の11行で、約1.498秒から末尾の約640.038秒まで
エラー5が継続していました。この間に取得できなかったIMU値は復元できません。
GPSの3D測位が有効な行も22,546行あり、IMU固有の停止を確認しました。

BNO055の内部エラー5は「レジスターマップのアドレス範囲外」を表します。
`SYS_STATUS=1` の場合に `SYS_ERR` を読むという条件に従って取得しています。
出典：[Bosch BNO055データシート、SYS_ERR](https://www.bosch-sensortec.com/media/boschsensortec/downloads/datasheets/bst-bno055-ds000.pdf#page=75)。
この内部エラーが最初に発生した電気的・通信上の要因までは特定していません。

従来はI2C通信が失敗した場合だけ再初期化していました。内部エラーがあってもレジスター読取りは成功するため、
復旧条件に入らずエラー状態を読み続けていました。さらに、読取り成功回数から `IMUHz` を計算していたため、
有効な値がなくても100Hzと表示されていました。

調査開始時にはUSB認識が一時的に通常と異なり、A105に応答しない区間もありました。
通信が戻った時点のIMUは正常でした。この接続変動と、SDに残っていたIMU内部異常の原因を同一とは断定していません。

## d版の対策

書込み済み版：`logger-v1-imu-recovery-20260831d`。

- I2C通信失敗、または有効な融合データがない状態が10回連続したら、IMUだけを再初期化します。
  読取りが100Hzで成功する内部異常なら約100msで検出します。通信タイムアウトがある場合は長くなります。
- 既存のBNO055リセット端子・NDOF設定処理を使用します。MCU・GNSSをリセットせず、SD記録も停止しません。
  初期化できない場合は間隔を空けて初期化を再試行します。
- 正常サンプルを得たら連続異常の回数をクリアし、一時的な遷移で毎回リセットしないようにします。
- `IMUHz` と `imuSamples` は実際に有効なデータを得た回数から計算します。
- `imuErrors` は、通信・初期化失敗に加えて内部状態異常の読取り回数も数えます。
- 復旧中のIMU値は空欄で残し、古い値を正常値として保持したり欠測を0で埋めたりしません。
- IMUが有効でない状態では校正値を保存しません。保存済み設定・補正値は削除しません。

正常な `SYS_STATUS=5` のときは、古い `SYS_ERR` の値だけを見てリセットしません。
復帰時には姿勢推定や校正状態が変化する可能性があります。完全校正・車体軸の確定は別途必要です。
PCを接続せず、SDだけで記録する場合にも復旧処理は動作します。

## 診断項目

`getStatus` の `IMU` に次の項目を追加しました。

| 項目 | 意味 |
| --- | --- |
| `validSamples` | 今回の起動中の有効サンプル数。 |
| `invalidSamples` | I2C読取りは成功したが、融合データが有効でなかった回数。 |
| `recoveries` | 連続異常による再初期化の開始回数。成功回数とは別です。 |
| `status` | 最後に読めた内部状態。5は融合処理動作中。通信断時は古い値になり得ます。 |
| `lastError` | 最後に読んだ非0の内部エラー。復帰後も残す履歴で、現在の異常判定には使いません。 |
| `diagnostic` | 復旧試験の状態。0=未実施、1=待機、2=停止指示成功、3=停止指示失敗。2は復帰完了の意味ではありません。 |

現在の有効性は、サンプル側の `IMULink`・`IMUErr`・`IMUHz` と合わせて確認します。
試験後の累計エラー数や再初期化数が0でなくても、現在の異常とは限りません。

## 実機試験と確認範囲

UART限定の `testImuRecovery` に `confirm: LOGGER_IMU_ONLY` を明示した場合だけ、
実際のBNO055をCONFIGモードへ切り替えて融合処理を止めます。正常運用では使いません。
この操作自体はGPS・SD・本体の再起動を指示しません。

3回実施し、3回とも通常の異常監視によるIMU再初期化と100Hzへの復帰を確認しました。
停止指示からUARTで100Hzへの復帰を確認できた時間は4.41秒、3.92秒、3.91秒です。
初期化、頻度表示の集計期間、診断通信の時間も含んでいます。

試験区間のSD CSVは1,808行、平均99.862Hz、最大行間隔29.774msでした。
停止に伴うIMU欠測519行が空欄で残り、その後に有効値へ戻りました。
SDキュー欠落・書込みエラーの増加はなく、同じファイルへの記録とGNSS受信処理が継続しました。
本体再起動はなく、既存のSDファイルも維持しました。GNSS受信処理の確認であり、位置測位の保証ではありません。

その後の約46秒の観測では、有効IMUサンプル・SD行数ともに4,566増加し、新しいIMU異常・再初期化・SDエラーはありませんでした。
RaceCaptureの画面でもGForce値とIMUHz=100.0を確認しています。現在のGPSは衛星0・未測位で、位置は欠測表示です。
累計 `imuErrors=30`、`recoveries=3` は今回の3回の意図的な停止試験によるものです。

実機試験はCONFIGモードによる融合停止であり、内部エラー5そのものを意図的に発生させた試験ではありません。
実ログと同じ `SYS_STATUS=1 / SYS_ERR=5` は、同じ復旧判定を使うC++試験で確認しました。
C++のASan/UBSan付き試験と、実機の11項目の判定は合格しました。
内部エラー5の発生要因の解消や、長時間・実走での再発防止まで確認済みという意味ではありません。

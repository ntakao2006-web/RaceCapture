## 未合格

- GNSS MAX-M10M UART：9600 / 38400 / 115200 baudのUBX-MON-VER応答がすべて0 byte
- RESET_Nは解除前後とも論理1、ハードウェアリセット操作は可能
- U13 TXD→ESP32 GPIO15はリセット前後とも論理0。UARTアイドルは本来Highのため異常

次の実測点はU13-8 VCC、U13-7 V_IO、U13-6 V_BCKP、U13-2 TXDです。電源が正常ならU13-2/GPIO15のGND短絡、パッド濡れ不良、モジュール向き・実装状態を確認します。

### GNSS再加熱後の再試験

- U13周辺へフラックスを追加してはんだごてで再加熱後、診断ファームを再書き込みして再試験
- RESET_N：リセット前後とも論理1へ正常復帰
- U13 TXD→ESP32 GPIO15：リセット前後とも論理0のまま
- 9600 / 38400 / 115200 baud：すべて受信0 byte、UBX-MON-VER応答なし
- 再加熱前から状態変化なし

### GNSS TXDプルアップ切り分け

- 実測：LNA_EN約2.26 V、VCC_RF約3 V。RF電源部は動作している
- ESP32 GPIO15へ内部プルアップを追加して再起動
- TXD/GPIO15はRESET_N解除前=`1`、RESET_N Low中=`1`、解除後=`1`へ変化
- 内部プルアップなしでは0 V、ありではHighになるため、TXDネットのGND短絡ではなく浮き／未駆動の可能性が高い
- UBX-MON-VERは引き続き全baudで0 byte
- 最有力候補：U13-2 TXDまたはU13-3 RXDのモジュール端子とPCBパッド間のはんだ接続不良

### GNSS TX/RX入れ違い・SAFEBOOT切り分け

- カスタムフットプリントと公式上面ピン配置を照合：pad 2=TXD、pad 3=RXD。なお、この時点では実装写真とのpin 1方向照合が不十分で、後段の確認により180°逆実装と訂正
- GPIO15とGPIO16を交互に受信専用として監視し、ESP32からは送信しない安全な試験を実施
- GPIO15：9600 / 38400 / 115200 baudすべて0 byte
- GPIO16：9600 / 38400 / 115200 baudすべて0 byte
- RX/TXが実装上逆ならGPIO16側へ起動UART活動が出るはずだが、どちらも無活動。単純なRX/TX逆配線は否定的
- TIMEPULSE接続先GPIO8を入力プルアップし、内部1 kΩ接続先のSAFEBOOT_NをLowへ引かない状態でも結果は変化なし

### GNSS端子再はんだ後の全条件試験

- U13のモジュール上面端子でpin 2 TXD、pin 3 RXDの導通確認後、再はんだした状態で診断版を書き込み成功
- U13 TXD/GPIO15駆動判定：RESET_N解除中はESP32内部pull-upで`1`、pull-downで`0`
- RESET_N Low中もpull-upで`1`、pull-downで`0`
- したがってTXDネットは短絡ではなく、RESET_N解除中にもMAX-M10Mから駆動されていない高インピーダンス状態
- TIMEPULSE/GPIO8：4秒間0 edge、最終level=`1`
- 受信専用試験32条件すべて0 byte
  - GPIO15 / GPIO16の両候補
  - 通常極性 / RX反転極性
  - 9600 / 19200 / 38400 / 57600 / 115200 / 230400 / 460800 / 921600 baud
- GPIO8を入力pull-upとした試験に加え、RESET_N解除の瞬間だけGPIO8を強制HighとしてSAFEBOOT_N誤選択を積極的に排除
- 強制High後も全8 baudでUBX-MON-VERおよびPUBX要求への受信は各0 byte、合計0 byte
- 公式仕様ではRESET_N Lowを1 ms以上与えるとBBR内の設定を消去してコールドスタートするため、保存されたUART設定が原因である可能性も低い
- 公式pin-state表ではTXDはcontinuous modeとsafe boot modeの両方でOutput。Input pull-upになるのはsoftware standby modeだけ
- 今回は基板電源再投入後にも試験し、さらにRESET_Nでコールドスタートさせているため、software standbyの残留も説明にならない
- VIO_SEL open時のV_IO動作範囲は2.7～3.6 V。VIO_SELをGNDへ短絡すると1.8 Vモード（動作範囲1.68～1.98 V）になるため、U13-15のGND短絡は要確認
- ソフト側で除外できたもの：単純なTX/RX逆、UART極性違い、対応範囲内のbaud違い、SAFEBOOT_Nの弱いプルダウン、BBR内のUART設定
- 残る最有力候補：U13-7 V_IOの端子実電圧／はんだ不良、U13内部のI/O電源・UART出力段の故障、U13-2の導通試験では見つからない高抵抗接続
- 同時再確認：CPU 240 MHz・dual-core負荷で最大38°C、SD 4-bit/40 MHz 8 MiB照合合格（書込1.42 MiB/s、読込1.75 MiB/s）、CAN1/CAN2内部試験合格
- 今回のCAN外部物理バスFAILはJ4-J5ループケーブル未接続状態での結果。接続時32/32双方向合格の既存結果を取り消すものではない

### GNSS電源・選択端子の実測

- U13-7 V_IO：3.31 V。VIO_SEL open時の仕様2.7～3.6 V内で正常
- 電源OFF、U13-15 VIO_SEL－GND：3 MΩ。GND短絡による1.8 Vモード誤選択は否定
- 電源OFF、U13-13 LNA_EN－GND：9.686 kΩ。外付けR49=10 kΩは正常
- 上記によりV_IO給電、VIO_SEL、R49実装不良は除外
- V_IO=3.31 V、R49負荷約0.23 mAに対し、既測LNA_EN=2.26 Vは通常のHigh出力として低すぎる。TXD高インピーダンスと合わせ、U13がcontinuous modeへ移行していないか、内部I/O段が損傷している疑いが強い

### GNSSソフトウェア診断系の自己検証

- 回路・PCB・ネットリストを再照合：ESP32 GPIO15=U13 pin 2 TXD、ESP32 GPIO16=U13 pin 3 RXD
- UBX-MON-VER pollの独立チェックサム計算：`0E 34`で実装値と一致
- NMEA PUBX,00の独立チェックサム計算：`33`で実装値と一致
- RESET_N、TIMEPULSE、pull-up/downへ一切触れる前に、9600 baudで5秒受動監視＋MON-VER poll 2秒を実施：受信0 byte
- UART1内部ループバック：9600 / 19200 / 38400 / 57600 / 115200 / 230400 / 460800 / 921600 baudの全8条件で16 byte完全一致、全合格
- GPIO操作の対照試験（MAX-M10M RESET_N Low中）
  - GPIO15：出力Low時read=0、出力High時read=1で合格
  - GPIO16：出力Low時read=0、出力High時もread=0で不合格
- GPIO16はMAX-M10M動作中とRESET_N Low中の両方でHighへ駆動できず、同一ピンUART物理ループバックも0 byte
- PCBデータ上の`/GNSS_TxD`はESP32 U3 pin 9 (GPIO16)とMAX-M10M U13 pin 3 (RXD)だけに接続され、第三の部品接続はない
- 結論：UARTドライバ、baud設定、コマンド、GPIO試験コードは正常。現在の一次異常はGPIO16－U13 pin 3ネットがLowへ拘束されていること。原因は実装短絡、配線上の導電異物、ESP32 GPIO16端子損傷、U13 RXD入力クランプのいずれかで、U13単体故障とはまだ断定しない

## CANテストファームの修正

初回の外部接続試験ではCAN1→CAN2、CAN2→CAN1とも0/32で、TWAI TX error=8、bus error=1、MCP25625 REC=27だった。原因は診断ファームのMCP25625ビットタイミングが20 MHz水晶に対して誤っていたこと。

## U13逆実装の確定（2026-08-30）

- 電源OFFでU13基板pad 3（RXD）－GNDが短絡し、同一ネットのESP32 U3 pin 9（GPIO16）－GNDも短絡
- MAX-M10M公式上面ピン配置ではpin 12がGND。18ピンLCCを180°逆に置くと、基板pad 3位置へモジュール本来のpin 12が来るため、実測短絡と完全に一致
- 公式データシートでは赤いu-bloxロゴがpin 1 marking。実装写真では赤いロゴと基板F.SilkSの小円pin 1マークが対角位置にあり、U13は180°逆実装と確定
- 逆実装時は基板pad 2（TXD）位置へ実pin 11（RF_IN）が来るため、GPIO15側が高インピーダンスだった既測結果とも一致
- 逆実装時は本来のVCC/V_IO/V_BCKPが基板の未接続pad 17/16/15側へ来て給電されず、基板の+3V3は実pin 17/16/15（SCL/SDA/VIO_SEL）側へ加わる。UART無応答、低発熱、不自然なLNA_EN/VCC_RF電圧も説明できる
- 安全のため以後の通電・ソフト試験は中止。U13を取り外して向きを修正するまで再通電しない

## U13・ESP32再実装後の再試験（2026-08-30）

- PSRAM有効ファームではブートローダがPSRAM IDをvendor=`0x1c`、density=`256 Mbit`（32 MB）と誤読し、`cpu_start: Multicore app`直後にRTCWDTリセットを反復
- esptool/eFuseは搭載ESP32-S3を`Embedded PSRAM 8MB (AP_3v3)`として認識。診断ファームのみPSRAMを無効化すると約0.3秒で安定起動
- PSRAM無効状態では内蔵Flash、240 MHz dual-core負荷、温度計測（最大34°C）、SD 4-bit/40 MHz 8 MiB照合、CAN1/CAN2内部試験が合格
- GPIO16－GNDの以前のLow拘束は解消し、GPIO16出力Low/High read=`0/1`で合格
- GNSS 9600 baud受動監視は0 byte
- MON-VER poll 8 byte送信後の受信は同一内容8 byteだけ。後段でもMON-VER 8 byte＋PUBX 13 byte送信に対して受信21 byteで、MON-VER本文は空
- これはGNSS応答ではなくUART送信内容の物理エコー。U13 pin 2 TXD－pin 3 RXDのはんだブリッジ／短絡が最有力
- `find_mon_ver()`を修正し、仕様上最小40 byte未満のMON-VER本文を拒否すると、`GNSS UART exact poll echo`およびGNSS FAILを再現確認
- GNSS pin 2－pin 3短絡を解消するまでGNSS通信試験は未合格
- ESP32はPSRAM無効なら主要機能が動作するが、PSRAM通信異常は残存。3回の加熱後であり、モジュール内部PSRAM損傷またはESP32モジュール実装／電源品質を別途切り分ける

## IMU（AE-BNO055-BO）実装後試験（2026-08-30）

- 初回はI2Cモードと誤認して試験したが、ユーザー指摘とAE-BNO055-BO資料に基づきUARTモードへ訂正。初回I2C走査結果はIMU合否判断から除外
- モジュールpin 3 `SDA/T`はUART TxD→ESP GPIO17 RxD、pin 4 `SCL/R`はUART RxD←ESP GPIO18 TxD、pin 5 RESET→GPIO7
- Bosch公式UART仕様115200 bps・8N1、レジスタ読出し`AA 01 <reg> <length>`で実装。chip ID register 0x00の期待値は0xA0
- BNO055をRESET Low中にESP UART2内部ループバック：6 byte完全一致でPASS。壊れかけのESP32でもUART2ペリフェラル内部は正常
- 同じRESET Low中にGPIO18／IMU UART-TXネットを静的駆動：Low時read=0、High時もread=0でFAIL。モジュールRxDへ行く送信ネットをESP32がHighへ上げられない
- RESET解除後800 ms待ち、chip ID要求を200 ms間隔で5回送信したが全て受信0 byte。GPIO17（モジュールTxD側）はidle High
- 一次異常はGPIO18～モジュールpin 4ネットのLow拘束。候補は実装短絡、AE-BNO055-BOレベル変換回路／RxD側クランプ、ESP32 GPIO18パッド損傷
- モジュール資料上、出荷時はJ4/J5短絡のI2Cモード。UART設定はJ2/J5短絡、J3/J4開放なので現物ジャンパ状態も再確認が必要
- 診断ファームはBNO055検出後にNDOFモードでEuler（Yaw/Roll/Pitch）、加速度XYZ、ジャイロXYZ、温度、校正状態、システム状態を50 ms周期で取得する実装済み
- RaceCaptureへIMU実測12項目＋UART診断4項目を追加し、A105 UART0/COM8にもRCP応答を追加
- COM8へ`getVer`、`getCapabilities`、`getMeta`、`s(meta=true)`を直接送信し、31チャンネルの完全なJSON応答を確認。現在値は`IMULink=0 / IMUChip=0 / IMURX=1 / IMUTX=0`
- OTG VBUS senseは接続後`1`になったが、WindowsにはVID 303A/PID 4001のCDCポートが列挙されず、OTGデータ通信は未合格。RaceCapture応答の実証はA105 COM8経由
- ESP32はPSRAM無効構成で240 MHz動作とRaceCapture応答を継続できており、今回のIMU不通はCPU全体停止ではない
